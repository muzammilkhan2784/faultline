# Technical details

The short version is in the [README](../README.md). This page has the full detail.


**A code impact analyzer for Python.** Faultline maps a repository's functions, classes and calls into a
Neo4j graph, then answers the question every change starts with: *if I change this function, what breaks,
and which tests should I run?*

> A faultline is where a small shift makes everything connected to it shake.

![The Explorer showing 84 functions affected by a change to Flask's App.add_url_rule](screenshots/explorer.png)

## The question it answers

You are about to change `flask.sansio.app.App.add_url_rule`. What can this break?

- **84 functions** can reach it within three calls, **68 of them tests**.
- The graph above draws them as a shockwave: orange at the epicentre, cooling outward, tests as diamonds.
- The **Tests** tab hands you a command to paste, so you run the 68 tests that matter instead of the whole suite:

```bash
pytest tests/test_async.py tests/test_basic.py tests/test_blueprints.py tests/test_cli.py ...
```

That is one function in a 13,000-line codebase, analysed in under a second. The same question on Django
(400,000 lines, 44,000 symbols) has an answer in **4 ms at the median, 22 ms at p99**.

## Quick start

```bash
git clone https://github.com/muzammilkhan2784/faultline && cd faultline
docker compose up -d --build        # Neo4j, API and UI
```

Open **http://localhost:5173**, paste a GitHub URL (or click *pallets/flask*), and explore. The API docs
are at http://localhost:8000/docs. Or use the API directly:

```bash
curl -X POST localhost:8000/api/repos -H 'Content-Type: application/json' \
     -d '{"source": "https://github.com/pallets/flask"}'
# -> {"repo_id": "…", "status": "pending"}     poll GET /api/repos/{id} until "ready"

curl 'localhost:8000/api/repos/<id>/impact?fqn=flask.sansio.app.App.add_url_rule&depth=3'
curl 'localhost:8000/api/repos/<id>/impact/tests?fqn=flask.sansio.app.App.add_url_rule'
curl 'localhost:8000/api/repos/<id>/briefing?fqn=flask.sansio.app.App.add_url_rule'   # the four paragraphs
```

**Analysing your own code.** Only Python (`.py`) files are read. Three ways, easiest first:

- **Push it to GitHub** and paste the URL into the UI (public repositories).
- **With Docker**, the API runs in a container and cannot see your drives: copy the project into the
  `.repos/` folder next to `docker-compose.yml` and enter `/repos/your-folder-name`. (Or point
  `FAULTLINE_REPOS` at any folder of projects.)
- **From a terminal, no Docker and no database:** `faultline analyze path/to/project` (see below).

The web app needs a Neo4j database, and Docker is the easiest way to get one; the command-line analyzer does not.

**No Docker?** The analyzer needs no database at all:

```bash
cd backend && pip install -e .
faultline analyze path/to/your/repo --impact your_pkg.module.function
```

## Written for someone new to the code

Numbers and a graph are not an explanation, so the left panel of the Explorer answers in four short
paragraphs whenever you pick a function:

1. **What this function does**: where it lives, its docstring (quoted, not paraphrased), its size and complexity.
2. **What is affected if you change it**: how many functions can be reached, how many call it directly,
   which modules they sit in, and whether any are entry points that real users can trigger.
3. **Which tests to run**: how many tests reach it, the closest one, and a copyable `pytest` command.
4. **Where the risk is concentrated**: a low / moderate / high rating that says *why*, and the most
   complicated dependents to review first.

When the answer is zero, it says what the zero means. "Nothing calls this" is an entry point, a test, a
private helper, possible public API, or callers hidden by the confidence filter, and each is explained
differently. Pointing Faultline at something it cannot analyse (a JavaScript project, notebooks, an
empty folder) fails with the reason instead of reporting `0 files, 0 nodes, 0 edges`.

The text is **templated, not generated by a language model**: every sentence is computed from a number
in the graph, so it cannot claim something the analysis did not find, and it is unit-tested to 100%.
See [DECISIONS.md](DECISIONS.md) for the rules behind the risk rating.

## How it works

```
repo (local path | git URL)
      │
      ▼  discovery       find *.py, prune .venv / migrations / build …
      ▼  PASS 1 · parse  ast → definitions, imports, raw call sites, type facts
      ▼  symbol table    every FQN in the repo + per-module import table
      ▼  PASS 2 · resolve  each call site → target(s), with a confidence score
      ▼  writer          batched UNWIND into Neo4j, nodes before relationships
```

Two passes are required: a call to `helpers.format_date` cannot be resolved while parsing the file that
makes it, because `helpers` may not have been parsed yet. Pass 1 collects facts; pass 2 resolves them
against the complete symbol table. The analysis half needs no database, which is why the benchmark and
accuracy harnesses run on a laptop.

The graph stores `Repo`, `Module`, `Class` and `Function` nodes and `CONTAINS`, `IMPORTS`, `INHERITS`,
`INSTANTIATES` and `CALLS` relationships. Every `CALLS` edge carries a **confidence** and a **resolution**
(`exact`, `inferred`, `ambiguous`), and the impact query multiplies confidence along a path, so a
three-hop route through two guesses ranks far below a direct call.

## Call resolution

Python has no compiler that can say `obj.save()` means `models.User.save`. Faultline applies a fixed
ladder of lookups and attaches a confidence to whatever it finds. **When the answer is unknowable it emits
nothing and counts that in the stats.**

| Call | Lookup, in order | Result |
|---|---|---|
| `foo()` | nested function in the caller → enclosing function scopes → module globals → import table → `import *` targets → builtins → any module-level def of that name | exact 1.0 → star import 0.8 → builtin dropped → ambiguous ≤ 0.5 |
| `self.foo()` | the class → its bases, in declaration order → class-body alias (`session_class = Foo`) | exact 1.0; inherited 0.95; alias 0.9 |
| `super().foo()` | the bases only, never the class itself | 0.95 |
| `mod.foo()` | import table, following package re-exports and `import *` chains | exact 1.0 |
| `Class.foo()` | the class and its bases | exact 1.0 |
| `x.foo()` | `x`'s known type: `x = User()` **0.7**, a parameter annotation **0.9**, `x = get_user()` with `-> User` **0.6**, `self.db = Session()` **0.7** | inferred |
| `param.foo()` | every *method* named `foo`, confidence spread across them, capped at 0.5; halved for names like `get`/`pop`/`loads` that are almost always builtins; dropped above 10 candidates | ambiguous |

Two rules worth naming: **a variable assigned two different classes is dropped from the heuristic** rather
than guessed, and **preferring to drop an edge over guessing** is a design principle, since one wrong
high-confidence edge does more damage to trust than ten missing ones.

### The honest resolution breakdown

Every call site lands in exactly one bucket. This is Django, the hardest case here:

| Bucket | Call sites | |
|---|---:|---|
| Exact | 51,027 | one unambiguous target |
| Inferred | 5,700 | type heuristic, star import, alias |
| Ambiguous | 11,168 | several candidates, low confidence |
| External | 54,956 | stdlib / third-party, not modelled |
| Builtin | 14,936 | `len()`, `print()` … |
| Too vague | 4,349 | more than 10 candidates: dropped |
| Unresolved | 13,353 | could not be determined |
| **Total** | **155,489** | |

Of the 85,597 calls that could target code inside Django (everything except builtins and external libraries), **79.3% were resolved and 59.6% exactly**. A tool
claiming 100% for Python is guessing. Of Django's 13,353 unresolved calls, **97% are `Model.objects.filter/
create/get…`**: `objects` is installed on every model by a *metaclass*, so no static reading of a class body
can see it. That is the textbook limit of this approach, and it is reported rather than hacked around.

Impact latency is 100 random depth-3 queries after warm-up, on functions that have at least one caller.*

Things the numbers do not say on their own:

- **Django's write time is noisy.** The three runs took 17.8 s, 26.3 s and 18.4 s. Docker Desktop on Windows
  adds a virtual-disk layer, and Neo4j's housekeeping after the bulk delete between runs shows up as stalls.
  Expect it to be faster on Linux; the JSON keeps every run.
- **The first run is much slower.** Django's first parse of a fresh clone took 52.6 s in an earlier run (not committed) and
  7.5 s once cached. That is disk (and antivirus) work, not the parser, which is why the table is a median.
- **Django is 398k lines**, because tests are included and migrations are excluded.

### Two claims, measured

The ingestion section makes two claims. Both are measured by `run_benchmark.py`, not asserted:

| Claim | Without | With | |
|---|---:|---:|---|
| Batched `UNWIND` (1,000 rows) vs. one transaction per edge, 3,000 edges | 9.64 s | 0.16 s | **59×** |
| `MERGE` on `(repo_id, fqn)` with vs. without the composite uniqueness constraint, 4,000 nodes | 1.94 s | 0.11 s | **17×** |

The constraint result understates it: without an index each `MERGE` is a label scan, so the cost grows
quadratically with node count. The default batch size is **5,000**, not the more common 1,000, because a
controlled comparison on Django (alternating order, first pass discarded) wrote in ~9.2 s at 5,000 versus
~13.6 s at 1,000: five times fewer round trips.

## Accuracy

142 call sites were **hand-labelled by reading source**, never by copying Faultline's own answer, from a
seeded random sample of Flask, `requests`, and a fixture project. CI fails if precision or recall regress.

| View | Precision | Recall |
|---|---:|---:|
| Default view (confidence ≥ 0.5) | **100%** (66 / 66) | **100%** |
| Every emitted edge, any confidence | 89.2% (66 / 74) | 100% |
| Wrong-target edges | **0** | |

**Read [docs/ACCURACY.md](ACCURACY.md) before quoting those.** The sample is small (a 95% lower bound on
the default-view precision is about 94.5%, not 100%), Flask was used to tune the resolver, and one repository
(`requests`) was held out. Its *first* score was 81.8% at the default view and 69.2% across all edges. The
write-up lists what that exposed: a mislabel of my own, a scoring artifact, and real bugs. It also lists
everything the harness found on real code that a hand-built fixture never would have (namespace packages,
`import *` re-exports, closures, class-body aliases, `try/except ImportError` fallbacks).

The gate itself was mutation-tested: making every ambiguous guess fully confident still scored 0.94 on a
naive threshold, so the default-view gate is set at 0.95 and that mutation now fails three tests.

## Deliberately not built

Naming these is the point: each one is a week not spent on the benchmark, the accuracy harness or this page.

| Not built | Why |
|---|---|
| Incremental re-analysis | A full re-parse of Django takes ~10 s; invalidation logic is real complexity for little gain at this scale |
| Other languages | The value is in the depth of Python resolution, not breadth |
| Full type inference | Only the single-assignment, annotation and return-type heuristics; a type checker is a different product |
| Data-flow analysis | Call graphs answer *what calls what*, not *what values flow where* |
| Git history / blame | A different question (change over time) that needs a different model |
| Auth, multi-user | A local developer tool; adding accounts would be scaffolding, not substance |
| Cloud deployment | Runs locally through Docker Compose, by design |
| Job queue | `BackgroundTasks` plus a status field is a deliberate simplification. A real deployment would queue |
| VS Code extension / PR bot | Natural next steps, deliberately out of this scope |
| LLM features | None. Every edge is derived from the AST and can be explained |

## Known limitations

Named before anyone else can:

- **Metaclass and descriptor magic.** Django's `Model.objects` (see above), SQLAlchemy columns, anything
  installed by `__init_subclass__` or a metaclass.
- **`getattr`, monkey-patching, plugin registries, entry points** and any other dispatch decided at runtime.
- **pytest fixtures.** They arrive by parameter *name*, so `client.get(...)` in a test is unresolvable. This
  is the dominant source of ambiguity in Flask's own tests, and it means test selection under-reports tests
  that reach code only through a fixture.
- **Calls on call results:** `factory().method()`.
- **Base-class order** is declaration order, not true C3 linearisation, which is why inherited hits score
  0.95 rather than 1.0.
- **Dead code is reported as "candidates"**, never as fact: dynamic dispatch and callers outside the repo
  all cause false positives.
- **Python only.** A JavaScript, Go or Java project is rejected with an explanation, and Jupyter
  notebooks are not read (export with `jupyter nbconvert --to script`).
- **The briefing quotes the first sentence of a docstring**, nothing more, and a function without one is
  described by its shape and connections only. It reads calls; it never runs your code.
- **Python 2 and template files** with a `.py` extension fail to parse; they are recorded on the module and
  counted, never fatal.

## Security

`POST /repos` accepts a URL or path, which means user-controlled input touching the filesystem and network.
Mitigations, all in [`ingest/repo_source.py`](../backend/faultline/ingest/repo_source.py) and unit-tested:

- `https://` only: `file://`, `git://`, `ssh://`, `git@…` and URLs with embedded credentials are rejected
- clones go into a fresh `mkdtemp()` that is removed in a `finally`; `git clone --depth 1`, with a timeout
- `subprocess.run([...])` with an argument list, never a shell, and `--` before any user-supplied URL
- refs and commits are matched against strict patterns, so `--upload-pack=…` never reaches git
- local paths must resolve inside `ALLOWED_ROOT` (a `/repos-evil` sibling of `/repos` is correctly rejected)
- size caps: 500 MB and 20,000 Python files
- the only value ever interpolated into a Cypher string is `depth`, validated as an `int` in 1..10 twice
  (Pydantic, then again before formatting) because Neo4j cannot parameterise a variable-length bound;
  everything else is a real parameter, and an integration test attempts an injection

## Project structure

```
backend/
  faultline/
    parsing/     discovery · imports · scope · complexity · module_parser · resolver
    graph/       client · schema · writer · cypher (every query lives here)
    analysis/    impact · test_selection · briefing (plain-English text) · cycles (iterative Tarjan) · hotspots · dead_code
    ingest/      repo_source (the security boundary) · pipeline
    api/         FastAPI app, schemas, routes
    accuracy.py  the scorer behind the accuracy gate
  tests/         unit · integration (real Neo4j) · accuracy (142 labels)
  benchmarks/    run_benchmark.py · sample_call_sites.py · results/
frontend/        React + TypeScript + Vite + Tailwind + Cytoscape
docs/            ACCURACY.md · DECISIONS.md · screenshots/
```

## Development

```bash
make up            # Neo4j + API + UI
make test-unit     # no database needed
make test          # + integration tests against a live Neo4j
make test-accuracy # the hand-labelled precision/recall gate
make check         # ruff, mypy --strict, coverage gate (85%)
make bench         # the benchmark
```

CI runs four backend jobs plus the frontend: `quality` (ruff, format, `mypy --strict`), `unit` (Python 3.10
and 3.12, 85% coverage gate), `integration` (Neo4j service container, plus **the accuracy gate**), `docker`
(builds both images and runs the unit tests inside the API image) and `frontend`.

Design decisions, and where this deliberately departs from the original plan, are in
[docs/DECISIONS.md](DECISIONS.md).
